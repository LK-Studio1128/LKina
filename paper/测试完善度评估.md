## 二、尚存的缺口（按优先级）

### P1 — 审稿人大概率会要求补的
1. **统计显著性检验缺失**：Fig 1–3 的成功率对比（如 74.3% vs 58.2%，n=292）目前没有置信区间或 p 值。补 McNemar 检验（配对成功率）或 bootstrap 95% CI，工作量约半天。
2. **292 Zn²⁺ 数据集子集文件化**：论文引用了 Santos-Martins 的 292 复合物基准，但仓库只有结果没有（至少）≥20 例的输入子集。"建议"栏已列两轮，审稿风险高。
3. **消融实验（ablation）不完整**：`--metal_soft_weight` 有 CLI 但没有实测消融表；P1/P1+P2/P4/C3 各层贡献只有合成体系证据，缺真实共价体系的分层消融。

### P2 — 加强说服力
4. **真实共价体系 C3 vs 单阶段对比**：合成的高斯井扫描不等于真实口袋行为；28 个 Cys-Michael 体系有 P1/P1+P2 数据，但 C3 只有合成测试。
5. **与 GPDOCK 的定量对比缺失**：GPDOCK 报 94.3%（9360 复合物），论文只做了引用层面的讨论。至少在 1–2 个共同体系上跑一次直接对比，否则 Discussion 中"unprecedented accuracy"的邻句会很扎眼。
6. **运行性能基准**：软件论文通常给出 runtime/内存对比（LKina vs Vina 1.2.7，同硬件同 exhaistiveness）。目前完全没有性能数据。
7. **水桥、BVS 的真实体系验证**：BVS 14/14 是设计合成体系；若能对 ≥5 个已知氧化态的真实 PDB 金属位点跑 BVS 推断并对照文献氧化态，说服力大增。

### P3 — 锦上添花
8. **重复性/方差**：当前所有对接 single seed。补 5 seed × 代表性体系的方差表，回应"exhaustiveness 16 是否足够"的潜在质疑。
9. **CI 集成**：把 110-mode 快速子集（如 20 模式冒烟测试）挂 GitHub Actions，每次 push 自动回归。
10. **金属错误模式（negative control）**：故意用错误金属模式对接（如把 Zn 位点用 Cd 模式），展示模式选错的后果，验证 --metal_mode 的必要性。

## 三、软件论文结构性不足（非测试类）

1. **无安装性测试矩阵声明**：正文提到 macOS 14/13 + Ubuntu 22.04 编译矩阵，但没有 Windows 实测记录（只有 .bat 脚本）。若声称三平台，需至少一次 Windows CI 证据，或改为"两平台实测 + Windows 脚本未测"的诚实表述。
2. **缺少 Citations 元数据文件**（CITATION.cff / joss paper.md），投稿前应补。
3. **文档入口分散**：LKINA.md / LKINA.html / docs/（readthedocs）三处，建议在 README 顶部明确"canonical 文档"指向。
4. **License 声明的边界**：AG4 引擎参数数据 GPL-3.0 与 Vina Apache-2.0 的混合许可，建议在 NOTICE 中加一段"哪些文件属于哪个许可"的逐文件映射（已有雏形，可再明确）。

## 四、结论

当前测试体系**在"引擎功能正确性"维度已充分**（覆盖率类测试超出同类论文），**在"统计严谨性"与"真实体系消融"维度存在 P1 级缺口**。最优先补：统计检验 + 数据集子集文件化 + metal_soft_weight 消融。这三项完成后，测试部分可达到 SoftwareX/JOSS 的接收水位。
